# Кэширование ответов провайдера

Этот документ описывает одну [Capability][CAPABILITY-TERM].

Способность продукта отвечать на повторные обращения из общего кэша без платного запроса к провайдеру, пока ответ актуален.

## Ключевые сценарии

[Ключевые сценарии][KEY-SCENARIO-TERM] — stakeholder stories; не user stories и не [реквест][REQUEST-TERM].

### Повторный запрос не оплачивается

**Сценарий:** [Финансовая служба][SH-01] видит, что одинаковые запросы разных ИС к одним и тем же данным оплачиваются провайдеру один раз за срок актуальности, а не каждый раз.

**Инструменты:** общий для всех ИС организации кэш ответов, политики кэширования эндпоинтов.

**Outcome:** платное потребление снижается без изменений в ИС.

### Экономия достаётся потребителю

**Сценарий:** [Руководитель подразделения][SH-02] видит, что ответы из кэша не расходуют лимит ИС его подразделения и не попадают в распределение потребления.

**Инструменты:** ответ из кэша фиксируется в учёте отдельным нетарифицируемым исходом.

**Outcome:** подразделение платит только за фактические запросы к провайдеру и видит, сколько сэкономило.

### Свежесть под контролем

**Сценарий:** [Администратор продукта][SH-04] задаёт для каждого эндпоинта, кэшировать ли ответы и как долго они актуальны, исходя из того, как часто меняются данные провайдера.

**Инструменты:** политика кэширования эндпоинта: признаки одинаковости обращений, срок актуальности, запрет кэширования.

**Outcome:** экономия не достигается ценой устаревших данных в обычном режиме.

## Границы

### Входит

- Общий для инсталляции кэш ответов в пределах одной организации.
- Политики кэширования эндпоинтов.
- Решение «ответить из кэша или запросить провайдера» для актуальных ответов.

### Не входит

- Отдача устаревших ответов при недоступности провайдера — [CAP03-03](CAP03-03-degraded-mode.md).
- Подсчёт сэкономленных единиц — `CAP04-01`, `CAP04-02`.
- Кэширование между разными организациями в SaaS — запрещено ([QA-07](../../04-quality-attributes/QA-07-tenant-isolation.md)).

## Инварианты и углубление

### Инварианты (меняются редко по смыслу)

- Ответ из кэша не расходует лимит внутреннего ключа и не тарифицируется.
- Каждый ответ из кэша фиксируется в учёте как отдельный исход обращения.
- Ответ, полученный по контракту одной организации, не отдаётся другой организации.
- В обычном режиме ИС получает из кэша только актуальные ответы.

### Допустимое углубление (меняется чаще)

- Принудительное обновление кэша по запросу ИС.
- Заблаговременное обновление популярных ответов.
- Учёт заголовков кэширования провайдера.

## Открытые вопросы

- Лицензионные условия провайдера могут запрещать или ограничивать кэширование, срок хранения и передачу полученных данных между ИС организации. Как продукт отражает такие условия в политике кэширования.
- Допустимо ли кэшировать ответы, содержащие персональные и иные чувствительные данные, и как долго ([QA-05](../../04-quality-attributes/QA-05-secret-and-data-protection.md)).
- Должна ли ИС иметь возможность явно отказаться от ответа из кэша и чем такое обращение тарифицируется для неё.
