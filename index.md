# Замысел продукта

Источник правды о [замысле продукта](../../glossary/terms/product-intent.md): зачем существует продукт, для кого, из каких ограниченных контекстов состоит смысл, какие capability предоставляет и какими атрибутами качества обязан обладать.

Структура каталогов, id и правила именования — [product-intent-structure.md](../../playbook/workflow/product-intent-structure.md).

## Продукт

**Snooping Nomarch** — коробочный шлюз для REST-запросов организации к внешним поставщикам данных и сервисов. Он даёт комплексное решение для учёта, лимитирования, кэширования, мониторинга, трассировки и распределения потребления этих запросов.

Продукт нужен организациям, в которых несколько независимых информационных систем (ИС) обращаются к одному и тому же внешнему провайдеру по одному общему контракту. Провайдер видит только контракт и свой ключ доступа; распределение потребления внутри организации ему неизвестно и неинтересно. Snooping Nomarch становится единственной точкой выхода к провайдеру. Каждая ИС обращается через него по своему внутреннему ключу, поэтому организация:

- изолирует бюджеты: ни одна ИС не может израсходовать объём, выделенный другим;
- знает, кто, сколько, когда и чего потребил, при одном ключе провайдера на всю организацию;
- сверяет взаиморасчёты с провайдером по собственным данным;
- снижает платное потребление и переживает недоступность провайдера за счёт кэша;
- распределяет фактическое потребление по ИС и подразделениям для бюджетирования и отчётности.

Продукт поставляется как on-premise инсталляция для одной организации и как SaaS для многих организаций.

## Value proposition

### Для кого

Для организаций, в которых несколько независимых информационных систем (ИС) — обычно в разных подразделениях — обращаются к одному и тому же внешнему провайдеру. Организация заключает с провайдером один крупный контракт на всех и получает по нему один ключ доступа.

### Проблема

Общий контракт дешевле разрозненных, но превращает объём запросов в общий ресурс. Любая ИС из-за ошибки, всплеска нагрузки или злоупотребления может израсходовать и свой объём, и чужой.

Провайдер видит только контракт и свой ключ, а внутренних потребителей не различает. Поэтому без собственного учёта организация:

- не может изолировать бюджеты подразделений;
- распределяет затраты на провайдера «по оценке», что искажает управленческую и регламентированную отчётность;
- сверяет взаиморасчёты только по данным провайдера и не может обоснованно оспорить акт;
- планирует бюджет и объём следующего контракта без фактической истории и сезонности.

Вдобавок разные ИС раз за разом оплачивают одни и те же запросы, а даунтайм провайдера останавливает все ИС одновременно.

Каждой ИС для работы с внешними провайдерами нужны учёт, кэширование и мониторинг запросов, но встроить это в каждую систему — отдельная трудоёмкая задача, не связанная с уникальной бизнес-логикой ИС. Её обычно откладывают или делают по остаточному принципу, поэтому возможности либо отсутствуют, либо дублируются в каждой ИС по-разному.

### Решение

Snooping Nomarch становится единственной точкой выхода ИС к внешним провайдерам. Каждая ИС обращается через него по собственному внутреннему ключу. Ключ провайдера при этом остаётся внутри продукта, и для ИС работа почти не отличается от прямого обращения к провайдеру. В результате организация получает:

- **Изоляцию бюджетов.** У каждого внутреннего ключа есть лимит, и поведение при его исчерпании настраивается: жёсткий отказ, мягкий лимит с оповещением или овердрафт.
- **Точную атрибуцию.** Каждое обращение относится к ключу и к подразделению в дереве структуры любой глубины, поэтому продукт всегда ответит, кто, сколько, когда и чего потребил.
- **Сверку по своим данным.** Потребление считается по правилам тарификации провайдера: в штуках или по весам эндпоинтов, с учётом того, какие ошибки и повторы провайдер тарифицирует.
- **Экономию и устойчивость.** Повторные запросы обслуживаются из общего кэша и не оплачиваются. При недоступности провайдера продукт может отдать последние известные данные с явной пометкой об их устаревании, если это разрешает политика эндпоинта.
- **Распределение за период.** Фактическое потребление раскладывается по ИС и подразделениям для аллокации затрат и бюджетирования.
- **Наблюдаемость.** Деградация провайдера обнаруживается раньше, чем на неё пожалуются пользователи, а любое обращение можно проследить от ИС до ответа провайдера.

### Чем отличается

- **Комплексность.** Одна модель закрывает лимиты, учёт, сверку, кэш и наблюдаемость. Самописные решения обычно закрывают только одну из этих задач.
- **Общий сервис вместо N реализаций.** Учёт, кэш и мониторинг исходящих запросов строятся один раз в продукте и доступны всем ИС-потребителям; см. [DRV-09](02-drivers/DRV-09-shared-cross-cutting-gateway.md).
- **Честная экономия.** Ответ из кэша не расходует лимит и не попадает в распределение затрат, поэтому выгода достаётся тому, кто потребляет.
- **Подключение конфигурацией.** Новые провайдеры, контракты, ключи и ИС подключаются без доработки продукта.
- **Одна модель для двух вариантов поставки:** on-premise для одной организации и SaaS с изоляцией организаций-покупателей.

### Чего продукт не делает

- Не считает деньги и не формирует проводки: он распределяет количества, а стоимость рассчитывается вне продукта.
- Не преобразует данные провайдера и не объединяет ответы разных провайдеров.
- Не может помешать обращениям к провайдеру в обход себя. Это обеспечивается организационно, а при сверке такие обращения проявляются как расхождение.
